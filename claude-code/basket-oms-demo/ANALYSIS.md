# Basket OMS demo — analysis

Can Deephaven be the **front end of an equities order-management system**: a basket-entry
ticket, a basket list, an order blotter with a right-click context menu (modify / cancel /
route / split), and panels that react to each other? This document is the analysis that
the plan ([`PLAN.md`](PLAN.md)) and the contract
([`docs/13-basket-oms-demo.md`](../docs/13-basket-oms-demo.md)) are built on. It was
written before the code, against `ghcr.io/deephaven/server:42.4` with `deephaven-plugin-ui`
0.42 (the versions the other apps in this repo run on); anything the live verification
later contradicted is marked **(verified)** or **(changed)** in the plan.

---

## 1. Python or Java?

**Python.** The UI layer has to be Python; the domain core is written so that it does not
care.

| Layer | Choice | Why |
|---|---|---|
| Interactive UI (tables with context menus, dialogs, forms, toasts, dashboard layout) | **`deephaven.ui`** (Python plugin, 0.42) | It is the only Deephaven-native component framework. Its `ui.table` takes `context_menu` items with server-side callbacks, `ui.dialog_trigger` / `ui.dialog` give modal or popover dialogs, `ui.form` + `ui.text_field` / `ui.number_field` / `ui.picker` make tickets, `ui.toast` gives feedback, `ui.dashboard` / `ui.row` / `ui.column` / `ui.stack` lay panels out, and `ui.use_state` / `ui.use_memo` wire the panels to each other. There is **no Java counterpart**: a Java Deephaven application can publish tables and formatting (see `deephaven-app-java/` in this repo), but every interactive element still has to come from either `deephaven.ui` (Python) or a hand-written JavaScript plugin. |
| Order state (baskets, orders, executions, events, transitions, validation, splitting arithmetic, basket roll-ups, mock fills) | **plain Python, zero Deephaven imports** (`basket_oms_demo.core`) | Same pattern as `fix42cache` in the main app: unit-testable on the host without a JVM, and portable — a real OMS would replace this module with a gateway to the actual order server while the UI stays as it is. |
| Tables | Deephaven **keyed input tables** (`deephaven.input_table`, `key_cols=`) for baskets, orders and quotes; **append-only input tables** for executions and the audit log | Keyed input tables give upsert-by-key semantics, so a modified order updates in place and the blotter row keeps its position; append-only ones are the natural shape for a tape. Both tick, so every derived table (`natural_join`, `agg_by`, `tree`, `where`) updates live without a listener or a publisher. |
| Mock venue / market data | a daemon thread in the same process | Fills and quotes are generated by the core's `MockVenue.step()` (pure, seeded, unit-tested) and pushed through the same bridge as UI actions, so a fill arriving while a Modify dialog is open exercises exactly the concurrency a real OMS front end has to handle. |

What the Java route would have cost: a custom JS plugin (React + the `@deephaven/…`
packages) for the context menu and dialogs, a build pipeline for it, and a Java server-side
plugin to expose the actions. That is the *production* answer when a team already owns a
React code base, and §7 says what would move there; for a feasibility demo it is the wrong
first step.

## 2. What `deephaven.ui` 0.42 gives us, and where it stops

Facts read out of the installed plugin (`market-data-demo/.venv/.../deephaven/ui`), each of
which the plan turns into one step with a live check:

| Need | API | Note |
|---|---|---|
| right-click menu on the blotter | `ui.table(..., context_menu=[...])` | An item is `{"title", "icon"?, "description"?, "action": fn}` or a submenu `{"title", "actions": [...]}`; an entry may also be a **function** `(params) -> item | [items] | None` resolved when the menu opens, which is how items are hidden or disabled per row status. The callback's `params` carry only the **cell** (`value`, `text_value`, `column_name`, `is_row_header`, `is_column_header`), **not the row**. |
| know *which order* was right-clicked | `on_selection_change=` + `always_fetch_columns=True` (or `on_row_press`) | The component keeps the selected row in a `ui.use_ref` (and state); the menu resolver reads the ref. **(verified)** The grid selects the cell under a right-click, but the selection round trip lands *after* the menu items are resolved, so a menu opened on an unselected row shows generic *… selected order* items that resolve the order when clicked; a row selected beforehand gets the status-specific items. The `OrderId` cell's `value` is used directly when the click is on that column. |
| pop-up ticket | `ui.dialog_trigger(trigger, ui.dialog(ui.heading, ui.content, ui.button_group), type="modal", is_open=state, on_open_change=...)` | **(verified)** Controlled `is_open=True` on a trigger mounted only while an action is pending (its trigger button `is_hidden`) opens a modal from a *context-menu action*. Dialog children must be `heading` / `content` / `footer` / `button_group`; the form goes inside `content`. |
| typed ticket fields | `ui.text_field`, `ui.picker`, `ui.text_area`, `ui.form(on_submit=dict)` | **(changed)** The dialogs are `ui.form`s with `name=` fields: the submit event carries the values, so a Save/Enter right after typing cannot race the debounced `on_change` round trip (`text_field` changes are debounced ~250 ms on the client; `number_field` commits on blur and snaps to `min_value + k·step`, so it is not used). Live previews (parse errors, split sizes) still come from `on_change` state. Forms cannot nest: the ticket is two sibling forms (line builder, basket). |
| feedback | `ui.toast(message, variant="positive|negative|…", timeout=ms)` | Called from any callback. |
| basket → orders master/detail | `ui.use_state(selected_basket)`, `ui.use_memo(lambda: orders.where(...))` | A `where` on a ticking input table is itself ticking; the panel re-renders only when the *selection* changes, the table keeps ticking on its own. |
| colours, progress bars | `ui.TableFormat(cols=, if_=, color=, background_color=, mode=ui.TableDatabar(...))` | Row/cell formatting rules on `ui.table(format_=[...])`. |
| hierarchy after a split | `deephaven.tree(orders, id_col="OrderId", parent_col="ParentId")` | A `TreeTable` renders natively; `ui.table` accepts it. |
| layout | `ui.dashboard(ui.column(ui.row(...), ui.row(...)))`, `ui.panel(title=)`, `ui.stack(active_item_index=)` for tabs | `ui.flex` blocks grow by default and ignore `flex_basis` (found in the market-data verification); explicit `width=` / `height=` on `ui.row` / `ui.column` / `ui.stack` is what works — `ui.panel` takes no `width` **(verified)**. |

Where it stops (and how the demo copes):

- **No row in context-menu params.** Solved by selection tracking (above).
- **In-grid editing is the wrong kind of easy.** A table derived from an input table
  *inherits* its `InputTable` attribute, so the blotter grid came up editable (typed
  cells would have gone straight into `oms_orders`, bypassing the core) with *Delete
  Selected Rows / Paste* in its menu **(verified)**. The views strip the attribute
  (`without_attributes("InputTable")`); Modify is a dialog.
- **Dialogs are re-rendered from the server on every state change.** Keep dialog state
  small (five fields), never put a ticking table in a dialog.
- **Selection state is per client.** Two browsers on the same dashboard each keep their own
  selection but share the order tables — exactly what a multi-trader blotter needs; the
  audit log's `User` column shows which client did what (a trader name typed once per
  session, since the demo runs with anonymous auth).
- **`ui.table` is virtualised**: `on_selection_change` only carries columns listed in
  `always_fetch_columns`; `True` fetches all — fine for a blotter of hundreds of rows.

## 3. Popup or not? — how the trader creates a basket

Three ways to build the "new basket" entry, with the trade-offs as they apply to
`deephaven.ui`:

| Option | Shape | Pros | Cons |
|---|---|---|---|
| **A. Modal dialog** (`dialog_trigger(type="modal")`) opened by a **New basket** button in the basket panel's toolbar, and also by "Add orders…" on a basket's context menu | Name, strategy, trader, then either a **paste box** (`SYMBOL SIDE QTY [MKT\|LMT px] [TIF]` per line) or an **add-a-line** form that accumulates lines into a staged list, a preview of the parsed lines with per-line errors, and **Create** / **Create & route to ▾** / **Cancel** buttons | The trader's mental model (ticket → confirm); the dashboard behind it does not shift; one component reused for *Add orders to basket*; validation before anything is created | Cannot see the blotter tick while the dialog is open; long baskets need the paste box |
| B. Always-visible **Ticket panel** in the layout | The same fields in a `ui.panel` next to the baskets | Nothing hides the blotter; keyboard-friendly | Costs ~25 % of the screen permanently for something used a few times a day; "which basket am I adding to" becomes ambiguous |
| C. **Popover** anchored to the button (`type="popover"`) | Small form | Light | Too small for a multi-line basket; not for the demo |

**Decision: A**, with B available as a switch (`OMS_TICKET_PANEL=true` renders the same
component inline instead of in the dialog — one flag, one `if`). The **Modify / Route /
Split / Cancel** actions are also modal dialogs opened *from the context menu*: Modify
shows the current values and edits Qty / Limit / TIF; Route is a submenu of venues (one
click, no dialog) with a dialog only for the basket-level "route everything"; Split asks
for slice count *or* an explicit quantity list and previews the child sizes; Cancel is a
confirm dialog (one click on the wrong row must not cancel an order).

## 4. Data model (what the tables hold)

Frozen names are in the contract; this is the reasoning.

- **Two keyed input tables, `oms_baskets` (key `BasketId`) and `oms_orders` (key
  `OrderId`)**, hold *state*. Every mutation — UI, console API or the mock venue — goes
  through the Python core first (it validates, assigns ids, computes `Leaves`, `AvgPx`, the
  basket roll-up status) and is then *mirrored* into the input tables as an upsert. The
  core is the single source of truth; the tables are its live projection. The alternative
  (tables as the truth, callbacks doing `where` + `update` on them) puts business rules in
  UI code and cannot be unit-tested on the host.
- **`oms_events` and `oms_executions` are append-only input tables**: an audit tape and an
  execution tape, both filterable by the selected basket / order.
- **`oms_quotes` (key `Symbol`)** is a small ticking quote board fed by the mock venue, so
  the blotter shows `Bid / Ask / Last` beside each order through a `natural_join` — the one
  join that makes the blotter *feel* like an OMS screen rather than a static grid.
- Derived, all ticking, all built once at startup:
  `oms_baskets_view = oms_baskets ⋈ agg_by(orders by BasketId)` for the top panel (order
  count, live count, filled %, notional), `oms_orders_view = oms_orders ⋈ oms_quotes` for
  the blotter, `oms_orders_tree = tree(oms_orders)` for split hierarchies.

Order life cycle (subset of FIX 4.2 `OrdStatus`, with `SPLIT` added for a parent whose
quantity was sliced into children):

```
NEW ──route──▶ ROUTED ──ack──▶ WORKING ──fill──▶ PARTIAL ──fill──▶ FILLED
 │               │                │                 │
 │               └───reject───▶ REJECTED            │
 ├──cancel──▶ CANCELLED ◀───cancel─────────────────┘
 └──split───▶ SPLIT (parent; children start NEW in the same basket, ParentId set)
modify: allowed in NEW / ROUTED / WORKING / PARTIAL; Qty may not go below Filled
```

A basket's `Status` is rolled up: `STAGED` (every order `NEW`), `WORKING` (any order
routed and not done), `DONE` (all orders terminal, at least one filled), `CANCELLED` (all
terminal, none filled), `PARTIAL` is not a basket state — the `PctFilled` column says it.

## 5. The interactions the demo has to show

```
 New basket ──▶ dialog ──Create──▶ core.create_basket ──▶ oms_baskets / oms_orders upsert
                                                         ▲            │
 select basket row ─────────────▶ selected_basket state ─┘            ▼
                                        │                     oms_baskets_view ticks
                                        ▼                     (Orders / Filled / Pct)
                       orders panel = oms_orders_view.where(BasketId == selected)
                                        │
 right-click order ─▶ context menu (items depend on Status)
     ├─ Modify… ─▶ dialog ─▶ core.modify ─▶ upsert (row updates in place, audit row)
     ├─ Route ▶ venue ─▶ core.route ─▶ ROUTED; mock venue acks → WORKING → fills
     ├─ Split… ─▶ dialog ─▶ core.split ─▶ parent SPLIT + N children (tree panel shows it)
     └─ Cancel ─▶ confirm ─▶ core.cancel ─▶ CANCELLED (Leaves 0)
 select order row ──▶ executions panel filters to it; events panel filters to it
 mock venue thread ──▶ fills + quotes ──▶ every panel above ticks without a refresh
 basket context menu ─▶ Route all… / Cancel basket / Add orders…
 toasts after every action; the audit tape shows who did what
```

## 6. Risks and how the plan handles them

| Risk | Mitigation |
|---|---|
| Right-click does not select the row under the cursor | It does, but the selection lands after the menu is resolved **(verified)**: the resolver uses the `OrderId` cell value when the click is on that column, else the tracked selection, else generic items that resolve on click. |
| Dialog cannot be opened from a context-menu action (controlled `is_open` ignored) | Not needed — it works **(verified)**; the inline variant survives as `OMS_TICKET_PANEL=true`. |
| Concurrent mutation: a fill lands between the Modify dialog opening and Save | The core validates at commit time (`Qty >= Filled`), returns a typed error, the dialog shows it. The mock venue runs on purpose. |
| `deephaven.ui` callbacks and the venue thread both call `InputTable.add` | `InputTable.add` takes the update-graph lock itself; the core holds its own `threading.Lock` around each mutation, so the projection is always of a consistent state. |
| Heap: another Deephaven stack may be up on the 6 GB podman machine | Own compose file, `DH_XMX` default 2g (input tables are tiny), `DH_PORT` override. |
| Version drift of `deephaven.ui` | Every optional widget is built through the `_first(...)` fallback ladder the market-data dashboard already uses. |

## 7. What would change for a real OMS

- `core.OmsCore` becomes a client of the real order server (FIX 4.2 `D / F / G` out,
  `8` in); the table bridge stays; the UI stays.
- Entitlements: the dialogs' `Trader` field becomes the authenticated user (Deephaven's
  auth handler), and the context-menu resolver hides actions the user is not entitled to.
- Persistence / restart: replay the execution tape into the core at startup (the main app
  in this repo already does this from Kafka).
- Scale: hundreds of thousands of orders per day are fine for keyed input tables; the
  blotter stays a `where` on the selected basket, so the browser never sees more than one
  basket's rows.
- If the front end must be a bespoke React app, the `deephaven.ui` components map 1:1 onto
  `@deephaven/components` + `@deephaven/iris-grid`; the tables and their names do not move.
